# Motion Garden as an open agentic website

This folder makes Motion Garden an open agentic website, as defined in the
[Worldwide Agentic Web MVP spec](https://github.com/cognizant-ai-labs/agentic-web/blob/main/docs/worldwide_agentic_web_mvp_spec.md).
It was built with the agentic-web repository's `agentify-website` skill, adapted from a
static site to this Next.js app.

- **Network URL:** `https://motion-garden.netlify.app/agent/motion_garden`
- **Manifest:** `https://motion-garden.netlify.app/agent/agent-manifest.json`
- **Where visitors use it:** the **Ask the Garden** button on every catalog page
  (`components/agent/AgentPanel.tsx`, mounted in `app/(shell)/layout.tsx`).

## What it does

The network has two agents:

| Agent | Job |
| --- | --- |
| `garden_guide` (front) | Finds components, explains their controls, opens them and tunes the live preview. |
| `integration_helper` | Reads one component's full integration brief and returns the install command, files, code and the steps for the visitor's stack. It exists so the long brief stays out of the guide's context on every other turn. |

They act through eight site actions. The model sees each as `website_<name>`:

| Action | Effect | What it wraps |
| --- | --- | --- |
| `get_bench_state` | read | The open component and each control's live value, default and range (`lib/agent/bench-bridge.ts`) |
| `search_components` | read | `GET /api/agent/search` (`lib/agent/search.ts`) |
| `describe_component` | read | `GET /api/agent/component/[slug]` (`lib/agent/describe.ts`) |
| `get_component_code` | read | `GET /api/agent/component/[slug]?brief=1&max=30000`, the same brief as the page's **Copy for Agent** button (`lib/registry/prompt.ts`). A longer brief is left out, and the answer lists the files and the Markdown link instead |
| `get_component_file` | read | `GET /api/agent/component/[slug]?file=<path>`, one shipped file with comments stripped, in parts of up to 28,000 characters (`lib/agent/files.ts`) |
| `open_component` | write | Client-side navigation to `/components/<slug>`, with optional starting values |
| `set_controls` | write | The bench's own nuqs setter (`useTunedProps().setMany`), after checking every value against the component's `PropSchema` |
| `reset_controls` | write | The bench's own reset |

Every write can be undone on the page, so nothing asks for confirmation. A refused
change returns `{ok: false, reason, field}` and changes nothing. The assistant declines
anything the site cannot do, such as creating components or editing the visitor's
project.

## What other sites get

A site that lists the network URL in an agent's `tools`, and `https://motion-garden.netlify.app`
in its `allowed_peers`, can ask Motion Garden after its visitor agrees on a consent card.
The network then runs in that visitor's browser, on their key. Through
`bridge/bridge-actions.js` it shares four reads with every origin (`"*"`), because they
return only public, MIT-licensed catalog facts: `search_components`,
`describe_component`, `get_component_code` and `get_component_file`. The bench actions
stay on Motion Garden's own page.

## What any agent gets, without the network

The same reads are plain HTTP, open to any origin and listed in `/llms.txt`:

- `/components/<slug>.md` is the whole integration brief as `text/markdown`, whatever its
  size (`app/api/agent/component/[slug]/md/route.ts`, through a rewrite in
  `next.config.ts`). Each component page names it in a `<link rel="alternate">`.
- `/api/agent/search` and `/api/agent/component/<slug>` answer in JSON. `robots.ts`
  allows `/api/agent/` and keeps the rest of `/api/` closed.

## Free tier

A visitor who has not connected an AI model gets two free questions a day, paid for by
the site's own OpenRouter key. It is on only when `OPENROUTER_API_KEY` is set and the
`agent_usage` table exists; otherwise the assistant asks for the visitor's own key, as it
does on a fork.

`site.js` asks `GET /api/agent/llm` before it boots. With questions left, it hands the
runtime that endpoint as its router, so the runtime calls
`POST /api/agent/llm/chat/completions` like any provider. The vendored runtime is not
changed: `boot()` already takes a key, a router and a model from the page.

The key sits behind a public URL, so the endpoint narrows every request before it pays
for one (`lib/agent/free-tier.ts`, checked by `bun run check:agent`):

- It answers only this site's own pages (the request's Origin must be the host it reached).
- The system message must be exactly what the runtime sends for one of this network's
  two agents: the instructions from `motion_garden.network.json`, then the runtime's own
  context. Text added before or after it, or a second system message, is refused.
- It carries only this site's own tools: the network's agents, the `website_*` actions
  in the manifest and the runtime's `render_cruse`.
- It ends in the visitor's message or a tool result, as the runtime's requests do.
- The server picks the model and caps the output. The caller's model and options are
  dropped. It runs free models only: `openrouter/free` by default, or the id in
  `AGENT_FREE_MODEL` when that ends in `:free`. A paid id there is ignored, so the key can
  never be billed through this endpoint.
- It counts per visitor and site-wide, per UTC day: 2 questions a visitor, 300 across
  the site, and 4,000 model calls site-wide. One question takes several model calls (a
  tool round trip, the helper agent), so each counted question allows up to 16. A call
  that is not itself a question runs only against a question already counted, so nothing
  runs before a question is spent or after the day's questions are used up. A call that
  the model never answers is taken back off the count.

The runtime's context is not retyped: `bun run gen:agent` reads it from
`public/agent/runtime` into `lib/agent/runtime-context.json`, and `bun run check:agent`
fails when that file is out of step. After updating the vendored runtime, run
`bun run gen:agent`; until then the endpoint would refuse every request.

What this does not stop: a caller can type anything in the user message, as a visitor can
in the chat, and a model may follow it. The system message bounds what the model is told
to be; the daily limits bound how much anyone gets; free models only means the key is
never billed. Off Netlify the first `X-Forwarded-For` entry is the client's own word, so
there the per-visitor limits can be dodged and only the site-wide ones hold. On Netlify
the address comes from `x-nf-client-connection-ip`, which Netlify sets itself.

The count is kept in Postgres (`agent_usage`, `lib/agent/free-tier-server.ts`) under a
SHA-256 of the day, the visitor's IP address (IPv6 cut to its /64) and a server secret.
No address is stored, and a hash cannot be linked from one day to the next. Rows older
than a week are deleted. People behind one address (an office, a home network) share one
count.

The panel shows the count, "Free questions left today: 1 of 2", and `site.js` reads it
again from the server after every question, so it stays true when someone else on the
same address has asked one. When a limit is reached the endpoint answers 429 with one
plain sentence. The runtime shows that as "⚠️ LLM HTTP 429: …" and sets its badge to
"LLM error"; `site.js` (`dressError`) turns the bubble into an error card labelled "Free
limit reached" and gives the badge the same words, since the model did not fail. A
visitor's own provider error keeps its status in the label ("LLM error · HTTP 401").

This is the "site absorbs the inference cost" case of the spec, not a BYOK proxy: a
visitor who brings a key never reaches this endpoint. Their browser calls their provider
directly.

## Privacy

With their own key, the assistant sends the visitor's messages, and the page data it
reads, to the AI provider the visitor picks in **AI model settings**. The key stays in
this origin's browser storage. It is sent only to that provider, never to Motion Garden
or to another site.

On the free tier the visitor has no key. Their messages, and the page data the assistant
reads, go through Motion Garden's server to a free AI model on OpenRouter. The server
does not log or store them; the model's provider has its own terms. The drawer says this
before the first message.

Everything in the network file, including the instructions, is public by design.

## Build and check

From the repo root, with `SKILL_DIR` set to `skills/agentify-website` in a checkout of
[cognizant-ai-labs/agentic-web](https://github.com/cognizant-ai-labs/agentic-web):

```bash
node SKILL_DIR/scripts/build_network.mjs public/agent/motion_garden.hocon --manifest public/agent/agent-manifest.json
node SKILL_DIR/scripts/build_network.mjs public/agent/motion_garden.hocon --manifest public/agent/agent-manifest.json --check
node SKILL_DIR/scripts/check_partner.mjs http://localhost:3000/agent/motion_garden
bun run check:agent
```

The skill's Node DOM tests are not used: they drive a static page script, and this
bench is a React app. `bun run check:agent` checks the action logic against the real
registry instead, and the actions were checked in a browser through the runtime's own
action registry.

## Hosting

The public files need `Access-Control-Allow-Origin: *`, and `runtime/sandbox-worker.js`
needs its own Content-Security-Policy. Both are set twice: in `next.config.ts` and in
`netlify.toml`, because the CDN serves `public/` without running Next. `bridge/` must not
send `X-Frame-Options` or `frame-ancestors`, since callers load it in a hidden frame.

## Limits

- The runtime is a patched copy of nsdeploy's, kept unchanged here.
- `write` actions run without a dialog. The spec asks to show writes first; every write
  here only changes the bench, which the visitor can undo.
- Every agent can see every `website_*` tool. Instructions scope them.
- The LLM provider must allow browser (CORS) requests. Hosted Otari, OpenRouter, OpenAI
  and Anthropic do.
- Briefs over 30,000 characters (40 of 163 entries on 2026-11-21, 31 of them not
  templates) are not sent through the chat whole. The assistant gives the install command, the file list and the
  `/components/<slug>.md` link for the visitor's coding agent, and reads single files with
  `get_component_file`.
- The assistant offers `shadcn add` only for what a tool result gives it: the `shadcn`
  commands in `describe_component` and `get_component_code` (`lib/registry/shadcn.ts`).
  Templates have none.
